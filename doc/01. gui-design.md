# GUI design

The signing desk is a Windows desktop application that lives in the tray, listens on a port, and
shows each signing request so a person can approve it, or lets it through on its own when told to.
This document is the design of what the user sees. The wire protocol, the authentication scheme and
the signing procedure have their own documents once decided; this one refers to them where it has
to.

The mock-ups that go with this document are on a private canvas (Signature Master Desk) and are the
reference for spacing, colour and copy. Where the two disagree, the mock-up is newer.

## Principles

1. **One window, three sections.** Requests, Log, Settings, in a left rail. There are no wizards
   and no dialogs beyond the two below. Everything about a request is visible on one screen before
   the Sign button is pressed.
2. **The state of the machine is always in view.** A footer on every section shows the
   certificate, the timestamp server, whether automatic signing is on and whether the PIN is
   remembered. Persistent banners sit above the content for the two states that matter: automatic
   signing on (orange) and a self-signed certificate in use (amber). Banners are not dismissable;
   they go when the state goes.
3. **Dangerous defaults are visible.** Automatic signing and a remembered PIN are off by default,
   are switched on only in Settings, and change the footer, the banner and the tray icon while on.
   The tray menu offers to pause listening but never to switch automatic signing on.
4. **Signing happens in the window and nowhere else.** The notification opens the request; it has
   no Sign action. The tray menu has none either.
5. **Follow the system.** Light and dark follow the Windows app mode and switch live. The window
   uses the native frame and title bar. Fonts are the system UI font (Segoe UI Variable), with a
   monospace face for refs, hashes, file names and addresses.

## Window

- Default 1280 x 800, minimum 960 x 640. The last size and position are restored.
- Closing the window hides it to the tray. Quit is in the tray menu and in the window's menu.
- Layout from top: title bar, banners (zero, one or two), body, footer (28 px).
- The body is a left rail of 200 px and a content area. The Requests section splits the content
  area again into a list of 360 px and a detail pane that takes the rest.

### Colour

The palette is Catppuccin (catppuccin.com), Mocha for the dark theme and Latte for the light one,
with the values taken as published; `Theme.qml` is the one place they live. Surfaces go from the
back of the window to the front: the rail is crust, the canvas is mantle, cards and the list are
base, borders are surface0. Text is the palette's text, muted copy is subtext0, captions are
overlay1. The accent is blue. State colours are used for one meaning each and never for
decoration:

| State | Catppuccin colour | Used for |
|---|---|---|
| Pending, attention | yellow | awaiting approval, the rail badge, the test certificate banner |
| Automatic signing | peach | the banner, the footer word, the tray bolt |
| Signing | blue | in progress |
| Signed | green | done |
| Refused, rejected, failed | red | any negative end |
| Expired | overlay0 | the job gave up |
| Unverified | yellow | a check that could not be made |

A banner is its state colour washed at about 16 percent over the canvas, with the text in the
state colour on dark and in a darker shade of it on light, so it stays readable on Latte's pale
ground.

## Requests

The list on the left holds every request the desk has seen since it started, newest first, with
filter chips above it: All, Pending, Signed, Refused. A row shows a state dot, the repository, the
age, the ref in monospace, and a one-line summary: file count, actor, state. A refused row carries
its reason in red instead of the summary. The selected row has an indigo left border and tint. The
rail's Requests entry carries a badge with the number of pending requests.

The detail pane, from the top:

1. **Header**: repository and ref as the title, then "Requested <time> by <actor> from
   <workflow / job, run N>" with the run as a link, and a state pill on the right.
2. **Facts**: a two-column card with Repository, Ref, Commit and Authenticated as. The last one
   names the identity the desk verified, in the words of the scheme that is chosen.
3. **Checks**: a list of what was verified, each with a green tick or a red cross and the reason.
   The list is the same for every request so the eye learns where to look: caller identity,
   owner, repository on the allow list, ref matches the allowed pattern, a certificate is in
   place, every file matches its manifest hash. A request with any cross is in the Refused state
   and shows no Sign button. An amber question mark means "unverified": the check could not be
   made (today: caller identity, until the GitHub scheme exists). Such a request can still be
   approved by a person who recognises it, but is never signed automatically.
4. **Files**: a table of Name, Size, SHA-256 (first and last four groups, full hash in the tooltip
   and on copy), Version (from the file's version resource), Signature (none yet, signing, signed,
   failed).
5. **Action bar** (pending requests): a Reason field, a Reject button and the primary Sign N files
   button. Reject sends the reason back to the job. Sign starts signing at once; there is no second
   confirmation, because the whole screen is the confirmation.

While a request is signing, the Checks block is replaced by a Progress list: checks passed,
approved (by whom, or automatically), one line per file for `signtool sign`, one for
`signtool verify`, then "Signed file ready for the job to fetch". The action bar turns into a status
line and a Cancel button; Cancel after `signtool` has started is best effort and the log records
whichever outcome it got.

Done requests keep their detail pane as it ended, with the final state in the pill and the outcome
in the Files table.

### States

```
received -> checking -> pending   -> signing -> signed
                     |           |          -> failed
                     |           -> rejected
                     |           -> expired
                     -> refused
```

`refused` is the checks' word, `rejected` is the person's, `expired` is the job's (it stopped
waiting), `failed` is signtool's or the card's. With automatic signing on, `pending` lasts no time
and the log says "automatic" in the By column.

## Log

An append-only table of every signature, refusal, rejection, expiry and failure: Time, Repository,
Ref, File, SHA-256, Outcome with its reason, By (the signer, "automatic", "checks" for a refusal,
"nobody" for an expiry). A search box and chips (All, Signed, Refused, Rejected, Automatic) filter
the view; nothing edits it. Export CSV writes the filtered view; Open folder opens the directory
holding the log file. The footer of the section names the log file's path and the certificate it
was written under.

## Settings

Four cards in a two-column grid; every change saves as it is made.

- **Signing behaviour**: Automatically sign (checkbox, with the warning in its description),
  Remember PIN (checkbox; switching it on opens the PIN dialog below; while on, a line shows which
  certificate has a stored PIN with Change and Forget buttons), Start with Windows.
- **Certificate**: the current certificate's subject, issuer, thumbprint, expiry and key provider,
  with a "self-signed, test only" pill when issuer equals subject; Choose from the user store
  (the Windows certificate picker, filtered to code signing certificates with a private key); Make
  a test certificate (creates a self-signed one in the user's store for development); the
  timestamp server URL; the path to `signtool.exe`, found automatically from the Windows SDK and
  editable.
- **Listening**: bind address and port, a live line saying whether the port is open and under which
  address the machine is reachable, Pause listening, and the work directory where a request's files
  live while it is open.
- **Who may ask**: the allow list the checks use: owner, repositories, allowed ref pattern. The
  authentication scheme is not decided; this card grows whatever it needs and says so in a note
  until then.

## Tray

The application starts in the tray when it starts with Windows. The icon is a shield, and its state
is told by a small change to it:

| State | Icon |
|---|---|
| Idle, listening | plain shield |
| Pending | shield with an amber count badge |
| Signing | shield with an indigo clock |
| Automatic signing on | shield with an orange bolt, for as long as it is on |
| Paused or port busy | greyed, struck-through shield; the tooltip says why |
| Attention | shield with a red mark: certificate missing or expired, last signature failed |

The menu: Open Signature Master, a disabled line with the pending count, Pause listening (or Resume
listening), Open the log, Quit.

### Notification

A new request that passed its checks raises a Windows notification: "Signature requested",
"<repository> <ref>, N files, by <actor>. All checks passed.", with Review and Dismiss. Review opens
the window on that request. A refused request raises one too, with the reason and only Dismiss.
With automatic signing on, the notification reads "Signed automatically" after the fact, so the
person still learns about every signature as it happens.

## The two dialogs

**PIN dialog** (Remember PIN switched on, or Change): names the certificate, explains where the PIN
is kept (Windows Credential Manager, this user, never a file or a log), takes the PIN, and on Check
and remember tries it against the card before storing it, since a wrong PIN stored would lock the
card on the third signature. With Remember PIN off there is no dialog of ours: the card's own driver
asks on every signature and the application never sees the PIN.

**Certificate picker**: the Windows system dialog, not our own.

## What this design does not do

- No multi-user, no roles, no remote approval. One person at one machine.
- No in-app view of the files beyond their facts. Nobody can judge a binary by looking at it; the
  checks are what approval rests on.
- No history across restarts in the Requests list; the Log is the history.
- No theme of its own beyond following Windows.

## Implementation notes for the Qt project

- Qt Quick Controls with the `FluentWinUI3` style gives the Windows 11 look, follows the system
  theme and accent, and needs no custom control templates. The indigo accent is set on the
  application palette rather than taken from the system, so the colours above hold.
- The window is one `ApplicationWindow` with a `StackLayout` over the three sections and a shared
  footer; banners are a `ColumnLayout` above the body bound to two booleans.
- Requests are a `QAbstractListModel` in C++ exposed to QML; the log view reads the log file
  through a model of its own and never writes.
- The tray is `QSystemTrayIcon` with five icon variants rendered from one SVG at startup; the
  notification is `QSystemTrayIcon::showMessage`, upgraded to a Windows toast with actions if Qt's
  message cannot carry the Review button.
- The PIN goes through the Windows Credential Manager API (`CredWriteW`, `CredReadW`) in C++; it
  never passes through QML as a stored property, only as the dialog's transient field.
